# Перезапуск сцен: проекция, ассеты и рендер

**История исследования.** Предложенная ортографическая диорама позднее отвергнута пользователем. Действующая реализация возвращает два выбранных полных интерьерных кадра и использует PixiJS/Canvas; актуальный контракт — [ROOM_CORNERS.md](ROOM_CORNERS.md). Сравнение движков ниже сохранено как исследовательский материал.

Исследование 7 октября 2026 года. Это техническое предложение для визуального перезапуска, а не уже выполненная миграция. Runtime и сохранённые 600 задач в рамках исследования не изменялись.

## Выбор

Сначала произвести один цельный эталон торгового зала из общей ортографической сцены; затем реализовать сцены обустройства на **PixiJS 8 / WebGL**, сохранив существующие TypeScript-правила, Definition, solver, worker, сохранения и DOM-интерфейс заказов. Переход всей игры в Unity сейчас не оправдан задачей. Unity можно использовать как редактор исходной 3D-сцены с экспортом 2D; также подходит Blender. В runtime остаются независимые растровые слои.

Самое важное изменение — способ производства сцены. Новый движок не выравнивает перспективу готовых картинок и не исправляет неверный масштаб товара относительно корзины. Пока одна сцена не проходит художественную проверку, не тиражировать её на склад, рынок и остальные локации.

## Что фактически работает сейчас

`package.json` содержит Vite/TypeScript и инструменты проверки; зависимостей Canvas.js, PixiJS и Unity нет. `hallSceneHTML`, `campaignSceneHTML` и карта возвращают HTML. Runtime рисует `<img>` и CSS-позиционирование, а головоломка тоже использует DOM-полки. Поиск в `src` не обнаружил `getContext` или WebGL-рендерер.

В `src/hall-scene.ts` камера — 1536 × 1024. Мебель задаётся рамками в процентах; товар ставится по отдельному `foot`. Для левой корзины есть поправка `matrix(.734,-.097,0,1,0,0)`, её товарные точки пересчитываются отдельно. Передний бортик — повтор целой корзины, из которого CSS-полигон вырезает предполагаемый край. Ткань, коврик и навес нарисованы CSS-полигонами. У общей северной витрины меняется asset для второго ракурса, а набор товарных координат задаётся отдельным условием.

`src/campaign-scene.ts` использует другой общий механизм: рамки x/y/w/h, опциональный `foot`, z или y. При карте каждый объект дополнительно переносится в рамку участка. Эти два механизма не имеют общей камеры, физического масштаба, опорных плоскостей, слотов и контракта окклюзии. Это объясняет техническую хрупкость нынешней сцены; художественная несогласованность требует отдельной проверки изображений.

## Сравнение вариантов

| Вариант | Что даёт | Цена и ограничения | Решение для «Лавки» |
| --- | --- | --- | --- |
| DOM/CSS | Уже есть; семантические кнопки, фокус и адаптивные панели; отдельные изображения и маски доступны средствами CSS | Множество независимых stacking context и ручных рамок усложняют сцену; нет общего редактора геометрии; производительность определяется реальным количеством узлов/фильтров | Сохранить для рабочего UI и поля; допускается для первого проверочного эталона |
| PixiJS/WebGL | Явный scene graph, локальные координаты, контролируемый порядок слоёв, спрайты/атласы и маски, остаётся в TS-проекте | GPU-контекст и текстурная память; дорогие маски/фильтры нельзя назначать каждому товару; требуется новая обвязка сцены | Предпочтительный renderer сцен после эталона |
| Unity Web 6, 2D | Редактор сцены, prefabs, SpriteRenderer, анимация; поддержка desktop и некоторых mobile-браузеров | Новый C#/WASM runtime либо JS↔C# мост; управление heap и `.data`; отдельное восстановление интеграции сохранений, solver, SDK, UI | Возможен, но переносить весь работающий проект ради статичных сцен сейчас дорого |
| 3D runtime | Общая геометрия, свет, реальная глубина и камера | Другой способ производства и оптимизации; 3D не требуется механике сортировки; несоразмерный объём для текущей задачи | Использовать 3D при авторстве, экспортировать 2D |

CSS поддерживает clipping и alpha/luminance masking; это не невозможность DOM. [W3C CSS Masking](https://www.w3.org/TR/css-masking-1/) описывает и маски, и создание отдельных stacking context. Решение о Pixi — вывод из структуры проекта и производственного процесса, не утверждение, что CSS не может рисовать хорошую сцену.

Официальная документация PixiJS рекомендует production WebGL; WebGPU ещё отмечен как экспериментальный, CanvasRenderer в v8 — coming soon. Не обещать автоматический Canvas 2D fallback. [PixiJS Renderers](https://pixijs.com/8.x/guides/components/renderers). Контейнеры дают локальные координаты и сортировку `zIndex`/`sortableChildren`; RenderLayers позволяют отделить визуальный порядок от логического родителя. [Scene Graph](https://pixijs.com/8.x/guides/concepts/scene-graph), [Render Layers](https://pixijs.com/8.x/guides/concepts/render-layers).

Unity Web 6.0 требует WebGL 2 и WebAssembly на desktop; официально перечислены iOS Safari 15+ и Chrome Android 58+. Старое обобщение «Unity Web не поддерживает мобильные браузеры» здесь неверно. Поддержка API не доказывает производительность нашей сборки. [Unity browser compatibility](https://docs.unity.com/en-us/engine/6000.0/manual/platform-specific/webgl/intro/browsercompatibility). Unity отдельно предупреждает о heap, росте памяти и распакованном `.data` в памяти; mobile требует настройки. [Unity Web memory](https://docs.unity.com/en-us/engine/6000.0/manual/platform-specific/webgl/develop/memory). Вызовы браузерного кода поддерживаются, но их интеграцию нужно реализовать. [Unity browser scripting](https://docs.unity.com/en-us/engine/6000.0/manual/platform-specific/webgl/develop/interactingwithbrowserscripting/web-interacting-browser-js-to-unity).

## Единая арт-система

1. Одна измеримая сцена помещения: размеры в метрах, стены и пол, свет, масштаб мебели. Один ортографический rig с закреплёнными наклоном, масштабом и экспозицией. Два ракурса зала экспортировать из этой же геометрии; это смена camera ID, а не произвольная деформация sprite.
2. У каждой мебели — контакт с полом, размеры и точки товара в собственной локальной плоскости. У витрины — отдельные поверхности полок; у корзины — допустимая область опоры и передний бортик. Геометрию слотов экспортировать вместе с арт-манифестом.
3. Экспортировать фон архитектуры, тени, заднюю мебель, товарную выкладку, передние бортики и передний декор отдельными прозрачными слоями. Рисовать передний край как самостоятельный спрайт. Не вырезать его повторно из полного изображения корзины приблизительным четырёхугольником.
4. Товары внутри комнаты получают world-варианты той же номенклатуры под общий rig. Иконки товаров в головоломке могут оставаться читаемыми крупными видами; идентичность товара сохраняется по id. Один фронтальный sprite на любую наклонённую полку не является обязательным ограничением.
5. Разрешить в runtime только равномерный масштаб группы камеры. Не подгонять форму предмета независимыми scaleX/scaleY и skew. При несовпадении возвращаться к исходной сцене, слоту или asset.
6. Убрать декоративные подписи категорий и фальшивые ценники из эталона; они не объясняют головоломку. Мелкие покупки должны менять осмысленное оборудование или отделку сцены. Коврик и текстиль допускаются после проверки общего материала/света, а не как CSS-заполнитель свободного места.

## Контракт сцены

Ниже — предложенный интерфейс; это не существующий API и не готовая раскладка.

```ts
type Vec2 = readonly [number, number];
type Vec3 = readonly [number, number, number];

interface SceneDefinition {
  schema: 'coastal-scene-1';
  id: string;
  artRig: string; // версия камеры, света, масштаба и исходной 3D-сцены
  cameras: Record<string, {
    projection: 'orthographic';
    designSize: Vec2;
    worldToScreen: readonly number[]; // матрица из авторской сцены
    background: string;
    safeUiPolygon: readonly Vec2[];
  }>;
  objects: readonly SceneObject[];
}

interface SceneObject {
  id: string;             // один объект в обеих камерах
  taskIds: readonly string[]; // уже существующие стабильные campaign taskId
  worldFoot: Vec3;
  footprint: readonly Vec2[];
  replaces?: readonly string[];
  cameraAssets: Record<string, {
    back: string;
    front?: string;       // готовый alpha-слой бортика/рамки/стекла
    shadow?: string;
    pivot: Vec2;          // точка контакта в исходном изображении
    pixelsPerMeter: number;
  }>;
  surfaces?: readonly {
    id: string;
    localPlane: readonly Vec3[];
    slots: readonly {
      id: string;
      point: Vec3;
      maxSizeMeters: Vec3;
      acceptedGoods: readonly string[];
    }[];
  }[];
}
```

`SceneState` получает только владение существующими taskId, цвета и краткое событие покупки. Он не создаёт Definition, не выдаёт награды, не пишет Attempt. UI-marker получает screen-anchor через ту же camera matrix; сама кнопка остаётся DOM с доступным названием и размером от 44 px. Размещение mobile меняет размер контейнера и UI, а не геометрию сцены.

Порядок отрисовки: архитектура → контактные тени → объекты пола по глубине контакта → внутренние слои каждого предмета → передняя архитектура → UI. Для полки недостаточно глобально сортировать каждый sprite по экранному y: товар на верхней полке остаётся внутри родительской мебели. Внутри одного отсека: back → задний ряд товара → передний ряд товара → готовый front rim. Сложные пересекающиеся предметы разбивать на authored back/front-слои.

Дно товара обязано попадать в свой slot и не пересекать боковые стенки; верх товара может естественно возвышаться над открытой корзиной. Маска нужна для формы боковых границ/окклюзии, а не для обрезки всего товара до плоскости дна. По возможности front-спрайт делает перекрытие без фильтра. Pixi отмечает стоимость большого количества масок, особенно sprite masks; атласы и уменьшенные mobile-текстуры рекомендуются официально. [PixiJS Performance Tips](https://pixijs.com/8.x/guides/concepts/performance-tips).

## Пакет, память и сохранения

На 7 октября 2026 года Яндекс указывает максимум 100 МБ для содержимого архива до ZIP-сжатия. Это ограничение платформы. [Загрузка игры](https://yandex.ru/dev/games/doc/ru/console/add-new-game). У репозитория отдельный более строгий gate `dist < 80 000 000` и цель 64 МБ. Смена renderer его не отменяет; при пересмотре бюджета менять проектное решение явно. Выбор технологии выше сделан по качеству процесса и цене миграции; запрет внешних host не используется как аргумент против Unity.

WebP экономит файлы, но RGBA-текстура 1536 × 1024 занимает около 6 МиБ до mipmaps и дополнительных буферов. Один большой атлас 4096² — 64 МиБ. Грузить atlas текущей комнаты, выгружать чужие комнаты; не держать 18 зон одновременно. Исходные `.blend`/Unity-сцены, PNG и reference остаются в репозитории вне dist. Размер итогового Pixi/Unity-пакета требует реальной сборки; утверждать заранее конкретный размер runtime нельзя.

600 закреплённых заказов, `seed`, версии, structuralKey, проверенные пути, taskId, кошелёк и attempts по проектам остаются прежними. Арт-схема имеет собственную версию и не повышает generator/content version. Если меняется смысл старой покупки, это отдельное продуктовое решение с явным отображением старого taskId на новый видимый результат; не переписывать им историю игрока.

## Проверка перед масштабированием

- Сделать эталон с одной витриной, одной корзиной, разными по высоте товарами и прилавком; пустое, среднее и финальное состояние. Второй ракурс — та же мебель и владение.
- Проверить desktop и 360 px, два ориентационных режима, alpha-края, контактные тени, масштаб и читаемость. Проверить покупки, переход ракурсов и повторную загрузку из старого schema 6.
- Измерить первый интерактивный экран, размер dist, texture memory и переключение комнаты на физическом Android/iPhone. Эмуляция Chromium этого не доказывает.
- На новом адаптере воспроизвести имеющиеся решения и проверки сохранений; renderer не может влиять на Definition или отправку троек. После runtime-изменения выполнить `npm test` и `npm run build`, записать фактическую границу QA.
- Только после удачного эталона переносить 138 работ и остальные комнаты. Это исследование не включает проверенный Pixi-прототип, Unity build или замеры физических устройств.
