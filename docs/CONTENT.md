# Подготовка и добавление контента

Полный выпуск проектируется по [CONTENT_MASTER_PLAN.md](CONTENT_MASTER_PLAN.md): 6000 заказов, 756 работ, шесть локаций/36 локальных этапов в шести глобальных Stage, стройка и возвращения. Конкретные задачи и цены — [CONTENT_CATALOG.md](CONTENT_CATALOG.md). Данные плана находятся вне runtime в `docs/content/full-product-plan.json`; planned-no-definition не является уровнем, который можно выдать игроку. Пакеты производства не являются сокращёнными публичными выпусками.

Версия 0.5.0 содержит тридцать закреплённых заказов и одиннадцать покупок первой лавки. Первые двадцать Definition не изменены. Холодный отдел добавляет три товара и отдельный ракурс. Производство проверяется каталогами, воспроизведением решений и browser UI; правила — GAME_DESIGN.md, результаты — QA.md.

Принято 6 октября 2026 года: 1000 заказов на локацию, локальные этапы 80/120/160/200/220/220, глобальные Stage с выбором доступных проектов. Ближайшая единица реализации — полный внутренний блок Stage 1–2, 600 заказов/138 работ. Проверки физических устройств и новичков нужны до выпуска и сейчас не останавливают производство. Плановые числа не заменяют готовые Definition, сцены и сквозную проверку.

## Контент для новой кампании

Цель — [CONTENT_MASTER_PLAN.md](CONTENT_MASTER_PLAN.md): торговый двор с шестью локациями и возвращениями. Готовы 30/80 заказов и 11/26 работ первого этапа. src/campaign-plan.json хранит плановые цели отдельно от реального каталога; завершение доступного блока не выдаёт завершение этапа. В конце внутренней сборки явно указать недостающий контент, а не оставлять обещание следующей цели без доступного заказа.

Каждый пакет связывает заказы, задачи обустройства и результат конкретного этапа локации. Для каждой задачи указать стабильный id, главу/этап, цену, предыдущие необходимые шаги, место на сцене и состояние до и после. Зависимости локальных этапов учитывают предыдущую ступень этой локации и обязательные результаты предыдущего глобального Stage. `route` — топологический каталог, не линейное прохождение. Доступные ветви текущей стадии можно выбирать независимо. Смена цвета не считается отдельным шагом обязательного развития. Стоимость всех обязательных задач этапа укладывается в звёзды доступных новых заказов: будущие закрытые этапы и повторы не финансируют обязательный переход.

Производство этапа начинается с трёх композиций: начало, середина, финал. Исходная лавка использует пустой интерьер. Первый этап нового здания начинается с заброшенного участка, включает мусор/демонтаж/растительность/пни/очистку/разметку, фундамент/стены/крышу/отделку и базовое оборудование. Строительные заказы выполняются в уже открытом здании; внутренние закрыты до taskId открытия. Последующие этапы начинаются с сохранённой построенной сцены. Затем подготовить фон и отдельные прозрачные слои мебели, оборудования, товаров и декора. Согласовать ракурс, свет, размеры, точки размещения и перекрытия. Замена мебели скрывает предыдущий слой; товары появляются в предусмотренных местах на её пустой основе. Проверить начало, каждую покупку и финал на desktop и 360 px, сохранение оформления, возвращение в старую локацию и восстановление после загрузки.

Слово «объёмный» в художественном задании описывает растровую иллюстрацию. Runtime использует 2D-файлы и фиксированные ракурсы. Все исходные PNG остаются в `docs/art`, упакованные WebP — в `public/assets`; задания и происхождение записываются в [ASSETS.md](art/ASSETS.md). Наполненный старый `shop.webp` относится к демоглаве и не служит пустой основой новой локации.

src/campaign.ts содержит одиннадцать готовых SHOP_STEPS, другие главы пока без заказов/покупок. Schema 1/2/3/4 → 5 сохраняет точную попытку и валюты. Ракурсы hall/cold — общая композиция игры и campaign.html, отдельный объект не дублируется покупкой при смене ракурса. Для новой главы нужны данные, сцена, заработок, покупки и переход.

## Мастерская

После npm run dev открыть http://localhost:5180/author.html; для production preview — http://localhost:4173/author.html. Это отдельный инструмент автора, без изменения игрового прогресса.

1. Выбрать рецепт и seed. «Создать раскладку» генерирует кандидата в worker, проверяет его и воспроизводит решение до победы. Последние 12 точных структур страницы исключаются; при перезагрузке история мастерской очищается.
2. Сравнить число товаров, типов, полок, свободных мест, задних рядов и замков. Найденные ходы не считать рейтингом сложности. Пройти поле самостоятельно, затем нажать «Заново» и воспроизвести «Шаг решения» до сообщения «Заказ готов!».
3. При ручных переносах исходный пошаговый путь отключается до «Заново». Исходная Definition остаётся прежней; экспорт не записывает случайное текущее поле вместо исходной задачи.
4. JSON можно редактировать или импортировать из файла до 100 КБ. После правки нажать «Проверить JSON и открыть». Недопустимые метаданные, товары, размеры рядов, замки или невоспроизводимое решение блокируют экспорт.
5. «Скачать проверенный JSON» ещё раз проверяет и воспроизводит путь. Для возвращения к уже выбранной задаче импортировать сохранённый файл; исключение повторов может выбрать другой кандидат даже с прежним seed.

Экспорт — подготовленный файл, а не автоматическая публикация в главу. Включение в каталог остаётся явным изменением репозитория и проходит build.

## Новый заказ

Закреплённые Definition находятся в **src/levels/chapter.json**, порядок — **src/content.ts / CHAPTER**, продолжение — **src/levels/shop-expansion.json**. `npm run content:produce-shop` производит продолжение офлайн, отвергает повторные структуры, воспроизводит пути и сохраняет уже закреплённые записи. Runtime всегда клонирует готовую Definition, не перегенерирует её по seed.

1. Сохранить выбранный экспорт. Назначить новый стабильный id, например morning-market. Он обозначает конкретный заказ, не версию генератора и не номер в списке. Уже выпущенный id не переиспользовать для другого заказа.
2. Добавить Definition в массив src/levels/chapter.json. Обновить id и number; сохранить shelves, seed, generatorVersion, recipe и verifiedSolution выбранного кандидата.
3. Добавить запись в CHAPTER с тем же id и profile и коротким name. customer и line остаются метаданными; обязательный сюжетный текст на игровом экране не показывать. number в игре определяется текущим порядком каталога. guidance: gentle допускается только у вводных заказов 2–3; автоматическое обучение не переносить на следующие заказы. lesson: transfer / tools / rear / crate хранит метаданные обучения. Обучение объясняет действие подсветкой нужной ячейки; переносам обучать только на подходящей ручной задаче.
4. Обновить CONTENT_VERSION. Проверить привязку orderIds в CAMPAIGN_CHAPTERS и цены задач обустройства, если меняется длина главы. Фиксированный LEGACY_IDS не пересчитывать из новых seed и порядка: это таблица уже выпущенных сохранений.
5. Выполнить npm test и npm run build. content:check требует ровно одну Definition на запись, уникальные id и структуры, воспроизведённые решения, локальные ресурсы и достаточное число звёзд для ремонтов. Структурный повтор требует осознанного нового решения и изменения политики проверки, а не случайного отключения gate.
6. Пройти новую задачу через браузер, включая результат/следующий экран и повтор, на desktop и ширине 360 px. Зафиксировать проверки и снимки в docs/QA.md и docs/screenshots.

Затемнение и обязательные переносы закреплены только за первым заказом. guidance: gentle включено только у заказов 2–3; src/guidance.ts запрещает автоматическое сопровождение после третьего даже при ошибочной метке автора. Новые механики объяснять справкой и обратной связью без показа решения. Кнопка «Подсказка» после третьего работает только по запросу: один показ одного хода. Оплаченный cache сохраняет бесплатное повторное обращение, но не включает подсветку при продолжении или отмене. Правила проверены tests/guidance.test.ts и UI-сценариями заказов 4/7/9.

Редактирование shelves требует нового проверенного пути. Координаты хода — [[полка, место], [полка, место]], индексы с нуля. В текущем формате обычный передний ряд — три элемента; rear — массив рядов по три. null — пустое место; unlockAfter — положительное количество отправок. Резерв создаёт помощь, он не включается в исходную Definition. Полоса «Запас» суммирует товары во всех rear, а не изображает состав переднего ряда или цель для переноса. При изменении скрытых рядов проверить сохранность общих количеств и воспроизвести раскрытие каждого ряда до победы. Валидатор допускает 1–6 обычных полок, до двух задних рядов на полке, до четырёх типов товаров одновременно, путь до 100 ходов, непустые метаданные до 200 символов. Основная глава использует budget: null.

## Новый товар и ремонт

Товары регистрируются в src/catalog.ts: стабильный короткий ключ, название, локальное имя файла и цвет. Добавить transparent WebP в public/assets и исходный PNG в docs/art с происхождением/заданием в ASSETS.md. Все проверки используют единый реестр; нельзя добавлять скрытый товар только в UI. При изменении набора, из которого выбирает генератор, повысить VERSION и повторить npm run content:audit. Закреплённые JSON и сохранения сохраняют свои исходные товары/версию; удаление выпущенного ключа требует миграции.

StructuralKey перебирает только участвующие типы, сейчас 2–4 одновременно. Реестр содержит 9 товаров. Для введения нового товара использовать goods/requireGoods вместе с новым выпуском генератора; сохранять закреплённые Definition. requireGoods ограничен числом типов рецепта и своим пулом. Увеличение одновременно участвующих типов требует измерения solver и worker.

Задачи обустройства и главы задаются в `src/campaign.ts`, слой каждого купленного id — в `src/campaign-scene.ts`, координаты — в общей `src/campaign-scene.css`. Для нового шага нужны стабильный id, цена, зависимости, видимый слой, полупрозрачное состояние цели, сохранение и проверенный результат. В `src/world.ts` задаются маркер на месте объекта и изображение ближайшего результата. Главная, осмотр и итог используют одни слои; основная кнопка начинает заказ либо сразу устанавливает доступный предмет. Обязательные текстовые карточки в основной путь не добавлять. Названия и кнопки помещаются при тексте от 16 px; проверять portrait и landscape без растяжения сцены.

`src/renovations.ts` сохраняет старые id/цены для миграции и оформление уже купленных предметов; не добавлять туда новые обязательные покупки. Изменения ранее купленных шагов требуют явной политики миграции без повторного списания. Build проверяет реальный каталог, локальные ресурсы и воспроизведение готовых решений. План отдельно проверяет 6000/756, зависимости глобальных Stage, внутренние строительные gates и финансирование. Текущий renderer/хранилище ещё обслуживает только первую лавку; новая модель проектов требует реализации, а не только генерации строк. Добавление нового порядка задач требует версии кампании и совместимости сохранений; оно само по себе не требует смены генератора.

Выполнить `npm test` и `npm run test:ui`. Последняя команда собирает production и проходит обучение, сохранения, все доступные заказы, покупки, продолжение прежнего финала и повторы на desktop и 360 px. Для новых глав расширить сценарии; автоматический путь не заменяет наблюдения на игроках.

## Помощь и магазин

Каталог `src/tools.ts` содержит подсказку, смешивание и лоток: цены 100/200/300 монет и этапы открытия. Покупка пополняет inventory и не меняет текущий заказ; применение в заказе расходует запас после проверки результата. Не возвращать автоматическое списание монет из игрового поля. При добавлении инструмента сохранить проверку исходной Definition, обработку отказов и совместимость сохранений; дополнить unit-тесты и сценарий магазина в `tests/ui/campaign.spec.ts`.

## Проверка серии и наблюдения

npm run content:audit проверяет seed audit-0…audit-99 каждого профиля без истории исключений и пишет docs/generator-report.json. Эта выборка измеряет проходимость и точные повторы, не интерес и не верхнюю границу всех seed. Ограниченный поиск без решения означает unknown; не выдавать такого кандидата игроку. Проверенный путь не считается кратчайшим.

Для наблюдения на игроках запустить игру с ?playtest=1. В настройках доступен экспорт последних 1000 событий **с момента этой загрузки страницы**. Журнал не отправляется на сервер и очищается перезагрузкой. Записать первый самостоятельный перенос, понимание рядов/замков, ошибки, время и выходы. Автоматическое прохождение по известному пути не доказывает понятность новичку.

Перед платформенным выпуском выполнять этапы RELEASE.md. SDK, реклама, платежи и облако не входят в процесс простого добавления контента.
